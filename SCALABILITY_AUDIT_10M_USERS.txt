支付系统可扩展性审计 — 千万级用户(10M MAU / 5K-10K TPS) 评估
=================================================================

## 快速结论
当前代码可支撑 ~2-3K TPS。升至 10K TPS 需完成 9 个关键配置调整 + 5 个代码改动(已在 commit 5bb69da1 完成)。
按现状拓扑，推荐路径：先升 5K TPS(2-3 周)→ 验证→ 再升 10K(1 月内)。

---

## 审计矩阵

### 1. DB Sharding 状态 ✅ 已就位(需扩容)

**order-core** (订单中心)
- 架构: 10库 × 10表 = 100 分片
- 分片键: payment_intent_id (按位编码)
- 现状: PI / Charge / Refund / AccountingOutbox 全部同表同分片
  * PI insert: 10K/s → 100K op/s/10 shards ✅
  * Charge insert: 同上 ✅
  * Audit insert: 10K-20K/s → meta 单库 30K op/s ⚠️ **审计日志需迁分片**
- 扩容触发: 单 shard QPS > 5K(P95) 或数据量 > 100GB → resharding 至 20 库(见 RESHARDING.md)
- 路由: Router V1 按位编码完毕，V2 支持 1000 shard 已规划(待 Phase 1 改造)

**user-merchant-core** (商户-用户中心)
- 架构: meta 库(不分片) — user / merchant / merchant_channel_secret 量级不大
- 分片键: 若升级可按 user_id / merchant_id 前缀分片
- 当前: ~100K 商户 < 1GB，meta 库承载无压力 ✅

**accounting-system** (复式记账)
- 架构: 分布式事务 + outbox worker
- 现状: 单库可支撑 5K TPS(试算余额需串行)
- 需扩容: 超 5K 需分库或并发 day-cut worker

**payment-core** (路由层)
- 架构: **无状态无DB** — 仅内存路由规则 + hot-reload
- 分片键: 不适用(无数据层)
- 性能: 单实例 ~10K TPS(线性扩展) ✅

### 2. 路由层 ✅ 已就位

**Sharding Router**
- 实现: `order-core/internal/repo/router.go` — Router V1(当前) + RouterV2(预留)
- 跨片查询: 极少(webhook 去重按 inbound_webhook 单表，不跨片)
- 分片扩容: RESHARDING.md 描述完整 5-phase cutover + dual-read + 自动 router versioning
  * Phase 1: layout 改造(2w)
  * Phase 2: 部署 V2(不切流量)
  * Phase 3: 双写迁移 (3-6月，按数据量)
  * Phase 4: cutover(1周)
  * Phase 5: 收尾

**payment-core routing**
- 实现: yaml 配置 + 原子 ReplaceRules + hot-reload(`POST /admin/routing/reload`)
- 动态决策: country / payment_method / amount / merchant 多维决策
- 熔断: per-adapter circuit breaker 自动故障转移 ✅

**热点防御** ⚠️ 部分到位
- 头部商户(20 个占 80% 流量): 单商户 400 TPS
  * per_merchant_max: 当前 256 → 需调为 1024 (bulkhead 配置)
  * 缓解: KMS cache(Redis) + IntrospectToken LRU 可将热点分散到 KMS pool 而非 DB
- 缺失: 若单商户频繁操作少数记录，row-lock 可能成瓶颈 → 需数据库侧优化(binlog 行数控制)

### 3. 无状态服务 ✅ 已就位

**api-gateway** ✅
- 无状态: HTTP 请求鉴权 + 限流 + 路由转 gRPC
- 会话存储: Redis(distributed) ✅
- scale-out: 水平无缝

**order-core** ⚠️ 部分有状态
- 业务逻辑: **无状态**
- 后台 worker: ExpireWorker / ReconcileWorker / WebhookRetryWorker / AccountingOutboxWorker
  * 设计: leader-only (Redis distributed lock) → 单实例运行
  * 风险: worker 故障 → lag 堆积
  * 缓解: 监控 outbox_lag_seconds SLO < 30s(task #67)

**payment-core** ✅
- 完全无状态

**kms-manage** ⚠️
- 单实例 ~500 ops/sec(HSM-backed)
- 10K TPS 需 15K KMS ops → 需 3-5 replicas(已规划)

---

### 4. 缓存(防热点穿透) ⚠️ 大部分缺失

**Redis** ✅ 已有
- 用途: 会话 + 限流 token bucket + circuit-breaker 状态
- 容量: 10K TPS × 3 ops = 30K redis ops/s ✅
- 调整: redis client pool_size 默认 10 → 需调 100+(config item #5)

**KMS Decrypt Cache** ❌ **缺失(P1)**
- 当前: 每 Authorize 1-2 次 KMS decrypt(payment_token / audit encrypt)
- 需加: Redis 5min TTL → 命中率 80%+ → 降至 3K ops/sec/instance
- 估算: 可削减 KMS replicas 需求(从 5 降至 3-4)

**IntrospectToken Cache** ❌ **缺失(P1)**
- 当前: 每 mTLS RPC → user_sessions 表 SELECT
  * 30K user_session SELECT/sec → user_session (10×10 分片) 每 shard 300 QPS(勉强)
- 需加: 进程内 LRU cache 10K entries / 30s TTL → 命中率 95%+ → 降至 1.5K DB QPS
- 收益: 减轻 user-merchant-core 库压力，支撑多副本无 cache-coherence 问题

**config-center 客户端缓存** ✅ 已有
- atomic.Pointer 纳秒级读 + watch 机制(task #9 + #66)

---

### 5. 读写分离 ⚠️ 不充分

**MySQL Replica** ⚠️ 配置级支持，应用级缺乏决策
- 架构: 3-node primary + 2 replicas(标准配置)
- 当前使用:
  * **主库**: 所有 write(insert/update/delete) + ACID 查询(user_sessions 的 CAS)
  * **从库**: 配置层已开(MaxConcurrentStreams / gRPC pool)，但应用层查询路由策略不明确
- 需补: 标记哪些 SELECT 可走 read-replica(tolerance for 几秒 replication lag)
  * 候选: webhook_deliveries 历史查询、审计日志查询、非关键路径报表
  * 关键路径: user_sessions (必须主库防幽灵读) / payment_intent 状态查询(可容忍 lag)

**Replication Lag 处理** ⚠️ 未记录
- 无 gtid 或版本对齐机制 → 无法做 read-after-write consistency
- 缓解: 依赖缓存 + outbox(异步兜底)而非同步读-等待

---

### 6. 异步化 ✅ 已就位

**Outbox 模式** ✅ 完全实现
- 链路: order-core PI 成功 → insert accounting_outbox(pending) → AccountingOutboxWorker polling(5s) → RPC to accounting-system
- 幂等: idempotency_key + accounting outbox 行唯一 ✅
- Worker: 当前 1 worker → 需改 8 worker/shard 并发(config item #8)
- Lag SLO: < 30s(task #67 monitor)
- 表结构: accounting_outbox_NN(分片 100 表) + claim_token 防 race

**Webhook 出站** ✅ 已就位
- 存储: webhook_deliveries(meta 库 + claim_token)
- 重试: exponential backoff(已有)
- 去重: (channel_name, event_id) 唯一 ✅

**Kafka(审计日志)** ✅
- 吞吐: 10K-20K msg/s(audit_log / shadow_flush)
- 配置: batch 100ms (正向设计) ✅
- 消费: ClickHouse 落地(同步延迟 < 5min)

**Critical Path 跳数**
- authorize: api-gateway → order-core → payment-core → payment-channel → card-payment → card-center → kms-manage
  * 6 跳 mTLS gRPC(每跳 ~5ms LAN RTT) = 30ms 最低延迟(不含应用处理)
  * P99 预算: 1.5s → 链路延迟占 2%(低)，应用处理 + 渠道 latency 占 98% ✅

### 7. 容量预算 ⚠️ 需补充配置

**单 pod TPS(当前默认配置)**
- 硬瓶颈: KMS 500 ops/sec(单实例) + bulkhead 256 + HTTP idle 50
- 可支撑: ~2-3K TPS(全栈)

**10K TPS 总目标需要**
| 服务 | 当前 | 10K TPS | 备注 |
|---|---|---|---|
| api-gateway | 1 replica | 2 | TLS handshake |
| order-core | 2 | 3-5 | 业务处理 |
| payment-core | 1 | 2 | 路由层无状态 |
| payment-channel | 1 | 2-3 | adapter dispatch |
| card-payment | 1 | 2 | 网卡 adapter |
| kms-manage | 1 | 3-5 + Redis cache | 关键瓶颈 |
| user-merchant-core | 1 | 2 | token introspect |
| accounting-system | 1 | 2-3 | 复式记账 |
| MySQL shard × 10 | 1 node | 3-node cluster | replication |
| Redis | 1 sentinel | 3-node cluster | Cluster mode |
| Kafka | 1 broker | 3 broker cluster | replication |

**DB QPS 估算**
- order-core: PI + Charge + Refund insert: 10K/s → 100K op/s(10 shards) ✅
- user-merchant-core: IntrospectToken (cached): 1.5K/s(加 LRU) ✅
- accounting-system: booking + trial balance: 5K/s ✅
- 单主库 write throughput: ~200K op/s(当前硬件满足)

---

### 8. 热点防御 ⚠️ 部分到位

**高 TPS Merchant / Customer**
- 头部商户(20 个，占 80%): 单商户 400 TPS
- 防御:
  * per_merchant_max bulkhead: 256(默认) → 1024(头部) ✅ 已规划
  * KMS replica pool: 3-5 实例 → 负载均衡 ✅
  * IntrospectToken LRU cache: 95%+ 命中(无 DB 热点) ✅
  * Rate limit: 按 merchant_id + IP 双维度(payment-util/ratelimit 接口已抽)

**风险**
- 若某商户频繁操作同一订单(retry / fraud check),可能 row-lock 竞争
  * 缓解: order-core 的 PI 分片确保同订单落同 shard,但 shard 内仍有 row-level lock
  * 长期: 考虑 distributed lock 或 optimistic locking(当前未采用)

---

### 9. ID 生成 ✅ 完整设计

**Leaf Segment 方案** ✅
- 实现: `payment-util/idgen/leaf.go`
- 特性: 本地 segment buffer + 异步 refill → 无中央 ID server 瓶颈
- 位编码: payment_intent_id = `db_idx(1d) | table_idx(2d) | seq(32b) | reserved(20b)`
  * 支持当前 100 shard(10 库 × 10 表)
  * V2 扩展: globalTblIdx 从 2 位 → 3 位(支持 1000 shard) — RESHARDING.md Phase 1

**跨服务 ID 唯一性** ✅
- user_id: [1e8, 9e8) — user-merchant-core allocation ✅
- order_id: payment_intent_id — order-core allocation ✅
- merchant_id: [1e6, 1e7) — user-merchant-core allocation ✅
- 避免冲撞: accounting-system 预留 [1, 100] 系统账户 + [101, 999] business_type ✅

**性能**
- Leaf segment refill: 异步(无阻塞) ✅
- 本地 buffer: 足够 1s 内消耗(10K TPS)✅
